# oss-design-harness

현업 디자이너의 판단 기준을 추출해, Figma MCP(`use_figma`)로 실제 화면을 만드는 하네스.
**이 파일은 뼈대만 있는 빈 템플릿입니다.** 각 단계의 `TODO`를 채우는 것이 곧 이 스킬을 만드는 작업입니다.

순서를 그대로 따라가는 것이 아니라, 아래 4단계가 각각 무엇을 판단해야 하는지에 집중합니다.

## 0단계 — 요구사항 정렬

화면을 만들기 전, 무엇을 만들어야 하는지 자체가 불확실할 때 실행한다.

- **레퍼런스/시나리오 소싱 방법**: TODO — 이 프로젝트 도메인에서 어떤 레퍼런스를 어떻게 모을지 (예: 유사 카테고리 앱 스크린샷 검색, 경쟁사 화면 캡처 등)
- **질문 형식**: 라벨형 질문 금지. 레퍼런스를 보여주고 "좋다/싫다 + 이유"를 자유서술로 받는다. IA/플로우는 다이어그램이 아니라 클릭 가능한 로우파이 또는 시나리오 내러티브로 체험시킨다.
- **판단기준 역추출 방법**: TODO — 자유서술 반응에서 어떻게 암묵적 기준을 뽑아낼지 (예시 1~2개)
- **가정 처리**: 확정 안 된 정보는 `brief.md`에 "이렇게 가정했습니다"로 명시한다.
- **산출물**: `brief.md` (템플릿: `templates/brief.md`)

## B단계 — 발산·수렴

무엇을 만들지는 정해졌으나 어떻게 만들지 정답이 하나가 아닐 때 실행한다.

- **독립 축 식별**: TODO — 이 프로젝트에서 후보를 가를 독립적인 축이 무엇인지 (예: 비주얼 무드, 정보 밀도, UX 직관성 수준 — 예시일 뿐, 실제로는 프로젝트마다 다시 뽑아야 함)
- **후보 생성 방식**: TODO — 축마다 후보 몇 개를 병렬 생성할지, 어떻게 생성할지
- **비교·수렴 방식**: TODO — 최소 2개 이상 다른 관점(페르소나)으로 교차 비평. 어떤 관점을 쓸지 (예: UX관점 / 개발호환성관점)
- **산출물**: `decisions.md` (템플릿: `templates/decisions.md`)

## A단계 — 구조적 사실 검증

화면이 다 만들어진 뒤, 데이터로 예/아니오 또는 수치로 검증한다. 스크린샷 없이 Figma 노드 속성만으로 확인 가능.

체크 카테고리 (항목은 고정, 기준값은 프로젝트마다 `brief.md`에서 캘리브레이션):

- [ ] 컬러 팔레트 일관성 — TODO: 이 프로젝트의 허용 팔레트/토큰 값
- [ ] 타이포 스타일 재사용 — TODO
- [ ] Spacing 그리드 준수 — TODO: 그리드 단위(8pt 등)
- [ ] 컴포넌트 재사용률 (신규 생성 대비 기존 인스턴스 비율) — TODO
- [ ] 레이어 네이밍 semantic 여부 — TODO: 네이밍 컨벤션
- [ ] Variant 상태 커버리지 (hover/disabled/loading/error/empty 존재 여부) — TODO

## C단계 — 미적·게슈탈트 판단

화면이 다 만들어진 뒤, 반드시 스크린샷을 렌더해서 실제로 봐야 판단한다. 데이터 조회로 대체 불가.

체크 항목 (1회차 심사 리포트 근거 — 실제 판단 기준 내용은 TODO):

- [ ] 시각적 위계가 한눈에 읽히는가 — TODO
- [ ] 여백 리듬의 체감 일관성 — TODO
- [ ] 정보 밀도 번잡함 여부 — TODO
- [ ] 클리셰/AI슬롭 여부 — TODO
- [ ] 엣지케이스(빈 상태 등)의 실제 완성도 — TODO

### C단계 실패 시 라우팅

원인을 진단해서 아래 셋 중 하나로 분기한다.

1. **국소적 결함** (표면 속성 하나의 문제) → 그 속성만 고쳐 C단계 재검. B단계로 돌아가지 않는다.
2. **방향 자체가 틀림** (국소 조정으로 안 고쳐지는 구조적 문제) → B단계로 회귀, 다른 후보 선택 또는 재발산.
3. **반복 실패** (B단계에서 후보를 바꿔도 같은 이유로 계속 탈락) → 0단계로 에스컬레이션.
