# oss-design-harness

현업 디자이너의 판단 기준(안목)을 추출해, Figma MCP로 실제 화면을 만드는 하네스.

## 이 파일의 상태 — 무엇이 채워졌고 무엇이 비었는가

- **채워진 것 = 구조.** 단계 진입 조건, 서브에이전트 배선, 검증자 격리, 판정 절차, 라우팅, 라운드 이력. 손대지 않아도 실행된다.
- **빈 것 = 판단기준.** `TODO`로 표시된 곳 — "무엇을 보고 좋다고 판단하는가"와 프로젝트별 기준값. **이걸 채우는 것이 곧 당신의 안목을 코드화하는 작업이다.**

## 절대 규칙 — 모든 단계에 적용

1. **에이전트는 `TODO`를 스스로 채우지 않는다.** 비어 있으면 사람에게 묻고 멈춘다. 추측해서 채우면 이 하네스의 목적(사람의 안목 추출)이 그 자리에서 무너진다.
2. **최종 "이 정도면 됐다" 판단은 항상 사람이 내린다.** 에이전트가 완료를 자체 선언하지 않는다.
3. **확정 안 된 정보는 침묵하지 않고** `brief.md`의 가정 로그에 "이렇게 가정했다"로 명시한다.
4. **검증하는 에이전트 ≠ 만든 에이전트.** A·C단계는 반드시 별도 Agent로 띄운다(각 단계 항목 참조).

## 진입 라우터 — 지금 어느 단계인가

파일 상태로 판정한다. 이 하네스는 별도 상태 저장소를 두지 않는다 — **산출물 파일이 곧 상태다.**

| 조건 | 진입 |
|---|---|
| `brief.md` 없음, 또는 무엇을 만들지 자체가 불확실 | **0단계** |
| `brief.md` 있고 `decisions.md`에 선택된 후보 없음 | **B단계** |
| 후보 선택됨, 화면 아직 없음 | 화면 제작 → **A단계** |
| 화면 있음 | **A단계** → 통과 시 **C단계** |
| C단계 탈락 | **라우팅**(맨 아래) |

산출물 템플릿은 `templates/`에서 프로젝트 폴더로 복사해 쓴다. Figma MCP 연결·툴명 확인은 `docs/figma-mcp.md`.

## 0단계 — 요구사항 정렬

무엇을 만들지 자체가 불확실할 때 실행한다.

**원칙: 자극은 표상이 아니라 체험이어야 한다.**

- **라벨형 질문 금지.** "모던한 게 좋으세요, 클래시컬한 게 좋으세요?"는 상대와 어휘 이해가 다를 수 있어 무의미하다. 구체 레퍼런스(스크린샷)를 보여주고 "좋다/싫다 + 왜"를 자유서술로 받는다.
- **IA·플로우도 다이어그램으로 보여주지 않는다.** 박스+화살표 다이어그램도 결국 또 하나의 전문 표기법이라 라벨형 질문과 같은 함정에 빠진다. 클릭 가능한 로우파이, 또는 구체 시나리오 내러티브("아침에 일어나서 앱을 켰다고 해봅시다…")로 체험시킨다.
- **라벨을 상대에게 요구하지 않는다.** 라벨링은 하네스가 한다.

**절차**

1. 레퍼런스를 모은다 — **TODO**: 이 도메인에서 어떤 레퍼런스를 어디서 어떻게 모을지
2. **한 번에 하나씩** 보여주고 자유서술 반응을 받는다. 여러 개를 한꺼번에 보여주면 상대가 비교 모드로 들어가 개별 반응이 흐려진다.
3. **반응 원문을 그대로** `brief.md`에 기록한다. **요약하지 않는다** — 요약하면 역추출의 근거가 사라진다. "산만하다"와 "정보가 많아 부담된다"는 다른 기준을 가리킨다.
4. 반응에서 암묵적 판단기준을 역추출한다 — **TODO**: 역추출 방법(예시 1~2개)
5. 추출된 값을 `brief.md`의 **키**에 채운다. 이 키들이 A단계 판정의 기준값이 된다(아래 A단계와 키 이름이 일치해야 한다).
6. 확정 안 된 것은 가정 로그에 명시한다.

**산출물**: `brief.md` (템플릿: `templates/brief.md`)

## B단계 — 발산·수렴

무엇을 만들지는 정해졌으나 **어떻게 만들지에 정답이 하나가 아닐 때** 실행한다.

### B-1. 독립 축 식별

후보를 만들기 **전에** 축을 나눈다. 축을 나누지 않고 풀스크린 후보를 통째로 비교하면, 상대가 무엇 때문에 그것을 골랐는지 뒤섞여(confound) 판단 근거가 남지 않는다.

- 축은 2~4개.
- **독립성 검사**: 한 축의 값을 바꿔도 다른 축의 값이 따라 바뀌지 않아야 한다. 따라 바뀌면 그건 두 축이 아니라 한 축이다 — 합쳐라.
- **TODO**: 이 프로젝트의 축이 무엇인지
  (참고 예시: 비주얼 무드 / 정보 밀도 / UX 직관성 수준 — **예시일 뿐이다. 프로젝트마다 다시 뽑아야 한다.**)

### B-2. 후보 병렬 생성 — 서브에이전트를 눈가림해서 띄운다

축마다 후보를 Agent로 **동시에** 띄운다. `축 개수 × 후보 개수`만큼 한 번에 보낸다(순차로 보내면 아래의 앵커링이 그대로 발생한다).

★ **각 생성 에이전트에게 다른 후보의 내용을 주지 않는다.** 프롬프트에 넣는 것은 "당신은 [축]=[이 후보] 하나만 만든다"와 `brief.md`뿐이다.

왜 이렇게까지 하는가: 한 세션이 후보를 순차로 만들면 두 번째 후보가 첫 번째에 앵커링되어 축이 자동으로 오염된다. "축을 분리하라"고 문장으로 부탁하는 것과, 에이전트를 서로 못 보게 격리해 띄우는 것은 결과가 다르다. **격리하면 confound가 구조적으로 불가능해진다.**

- **TODO**: 후보 생성 시 각 에이전트에게 줄 추가 지침이 있는지

### B-3. 교차 비평 — 페르소나를 독립 에이전트로

후보가 다 나오면 페르소나별 비평 Agent를 **동시에** 띄운다.

- 페르소나 **최소 2개**. **TODO**: 어떤 관점을 쓸지 (참고 예시: UX 관점 / 개발 호환성 관점)
- ★ **비평 에이전트끼리 서로의 평가를 주지 않는다.** 하나의 평가가 다른 평가에 앵커링되면 "다각도 검증"이 사실상 한 각도가 된다.
- ★ **후보를 만든 에이전트가 그 후보를 비평하지 않는다.** 생성과 비평은 반드시 별개 Agent 호출이다.

## A단계 — 구조적 사실 검증

화면이 만들어진 뒤, **Figma 노드 속성만으로** 예/아니오 판정한다. 스크린샷 불필요.

**실행 주체**: 화면을 만든 에이전트가 **아닌** 별도 Agent. 만든 주체는 자기 결과를 통과시키는 쪽으로 판정이 기운다.

**입력**: 대상 프레임의 노드 트리 + `brief.md`
**출력**: 항목별 `PASS` / `FAIL` / `SKIP`.

- `FAIL`이면 **위반 노드 경로와 실제 값을 전부 나열한다.** 개수만 세지 않는다 — 개수만으로는 고칠 수 없다.
- 기준값이 `brief.md`에 비어 있으면 `SKIP(기준값 없음)`으로 보고하고 **추측해서 판정하지 않는다**(절대 규칙 1).

항목은 고정이고, 기준값은 프로젝트별로 `brief.md`에서 읽는다.

- **기준**: `brief.md` → `tokens.color.allowed`
- **판정**: 허용 목록에 없는 색상값이 1개라도 있으면 FAIL

## C단계 — 미적·게슈탈트 판단

A단계를 통과한 뒤, **반드시 스크린샷을 렌더해서** 판단한다. 데이터 조회로 대체 불가 — 개별 수치가 다 맞아도 전체가 어색할 수 있고, 그게 이 단계가 따로 있는 이유다.

### 검증자 격리 — 이 단계의 핵심 장치

C단계 검증은 **반드시 별도 Agent**로 띄운다.

**주는 것**
- 렌더된 스크린샷 (필수)
- `brief.md`의 판단기준 섹션
- 아래 체크 항목

**주지 않는 것**
- `decisions.md` — 어떤 후보를 왜 골랐는지
- 제작 과정·설계 의도·지금까지의 대화 이력

왜: 제작 의도를 아는 검증자는 탈락 항목에서 **"의도가 이랬으니 괜찮다"로 자기변호**한다. 검증자의 무지가 검증력이다. 덧붙여, 실제 사용자도 의도를 모르는 상태로 화면을 보므로 검증 조건이 실사용 조건과 같아진다.

### 체크 항목

각 항목을 `PASS` / `FAIL + 무엇이 어떻게 보이는지 서술 + 스크린샷 상 위치`로 답한다. "개선 여지가 있다" 같은 중립 표현을 쓰지 않는다 — 판정이 아니라 회피다.

## C단계 실패 시 라우팅

C단계는 합격/불합격이 아니라 **원인 진단**까지 낸다.

### 진단 절차

1. `decisions.md`의 **지난 라운드 탈락 항목**과 이번 라운드를 대조한다.
2. 아래 표를 **위에서부터** 검사한다.

| 판정 | 조건 | 행동 |
|---|---|---|
| **3. 반복 실패** | 후보를 바꿨는데도 직전 라운드와 **같은 항목**으로 탈락 | **0단계로 에스컬레이션.** 요구사항 해석 자체가 틀렸다는 신호다. |
| **2. 방향 오류** | 표면 속성 하나를 고쳐서는 해결 불가한 구조적 문제 | **B단계로 회귀.** `decisions.md`에 새 라운드를 열고 다른 후보 선택 또는 재발산. |
| **1. 국소 결함** | 표면 속성 하나의 문제 (예: 카드 간격만 불균일) | 그 속성만 고쳐 **C단계 재검.** B로 돌아가지 않는다. |

**위에서부터** 검사하는 것이 중요하다 — 반복 실패를 국소 결함으로 오진하면 같은 실패를 무한히 반복한다.
