# oss-design-harness

**현업 디자이너의 판단 기준(안목)을 추출해, 에이전트에 최적화된 형태로 재구성하는 Figma-네이티브 디자인 하네스.**

VIBE MAFIA CLUB 하네스톤 2회차(2026-09-05)를 계기로 이너서클 코파운더들과 함께 만드는 오픈소스 프로젝트입니다.
지향점: `ui-ux-pro-max` 급, 현업에서 쓸 수 있는 수준의 skill.

## 이 레포의 상태 — 구조는 채워졌고, 판단기준은 비어 있습니다

두 가지를 명확히 구분합니다.

- **채워진 것 = 구조.** 단계 진입 조건, 서브에이전트 배선, 검증자 격리, A단계 판정 절차, 실패 라우팅,
  라운드 이력. **손대지 않아도 실행됩니다.**
- **빈 것 = 판단기준.** `TODO`로 표시된 곳 — "무엇을 보고 고급스럽다고 판단하는가"와 프로젝트별 기준값.

판단기준을 미리 채워서 예시로 주면, 참가자가 자기 안목을 꺼내는 대신 이미 있는 답을 검토하는 일이 되어
원래 목적(다양한 디자이너의 독립적 안목 수집)이 오염됩니다. 그래서 **비워 둔 것은 의도된 설계**이고,
`SKILL.md`에는 **에이전트가 `TODO`를 스스로 채우지 못하게 하는 규칙**이 들어 있습니다.

## 프레임워크 — 4단계 판단 구조

디자이너가 일하는 **순서**를 그대로 흉내내지 않습니다. 사람이 순서대로 일하는 이유의 상당수는 사람의
기억력·주의력 한계를 우회하는 것이지, 결과가 좋아지는 진짜 원인이 아닙니다. 대신 각 단계가 실제로
하려던 일(**판단 기준**)만 뽑아서, 에이전트가 잘하는 방식(병렬 생성, 다각도 교차 비평)으로 다시 구현합니다.

| 단계 | 시점 | 하는 일 |
|---|---|---|
| **0. 요구사항 정렬** | 화면을 만들기 **전** | 뭘 만들지 자체가 불확실할 때, 레퍼런스/시나리오를 보여주고 반응(좋다/싫다+이유)을 받아 암묵적 판단기준을 뽑아낸다. 라벨형 질문("모던한 게 좋으세요?") 금지. |
| **B. 발산·수렴** | 만드는 도중, 정답이 여러 개일 때 | 독립적인 축(무드/밀도/난이도 등)을 먼저 나누고, 축마다 후보를 병렬 생성해 비교·수렴한다. |
| **A. 구조적 사실 검증** | 다 만든 후 | 데이터로 예/아니오 확인 가능한 것 (spacing, 컴포넌트 재사용, 네이밍, variant 존재 여부). |
| **C. 미적·게슈탈트 판단** | 다 만든 후 | 스크린샷을 렌더해서 실제로 봐야만 아는 것 (색온도 일관성, 위계, 여백 리듬, 클리셰 여부, 엣지케이스 완성도). |

C단계에서 탈락하면 원인에 따라 세 갈래로 라우팅합니다 — ① 국소 결함(그 속성만 고쳐 C 재검)
② 방향 자체가 틀림(B로 회귀) ③ 반복 실패(0으로 에스컬레이션). 재시도 상한을 두고, 최종 판단은 항상 사람이 냅니다.

자세한 배경·논리 검증 과정은 킥오프 자료(`docs/concept.md`) 참고.

## 하네스 배선 — 문서가 아니라 강제 장치입니다

프레임워크를 문장으로 서술하는 것과, 지켜지지 않으면 불가능하게 배선하는 것은 결과가 다릅니다.
이 레포는 후자를 택했습니다. 세 가지가 핵심입니다.

**후보 생성 에이전트를 서로 눈가림합니다.** B단계 후보는 축별로 병렬 Agent가 만들고, **각 에이전트는
다른 후보를 모릅니다.** 한 세션이 후보를 순차로 만들면 두 번째가 첫 번째에 앵커링되어 축이 자동으로
오염되기 때문입니다. 격리하면 confound가 구조적으로 불가능해집니다.

**검증자에게 제작 의도를 주지 않습니다.** C단계 검증은 별도 Agent가 **스크린샷만 보고** 합니다.
`decisions.md`(어떤 후보를 왜 골랐는지)와 대화 이력은 주지 않습니다. 제작 의도를 아는 검증자는 탈락
항목에서 "의도가 이랬으니 괜찮다"로 자기변호합니다. **검증자의 무지가 검증력입니다.**

**산출물 파일이 곧 상태입니다.** 별도 상태 저장소나 카운터를 두지 않습니다. `decisions.md`의 라운드
이력이 재시도 카운터를 겸하고, 라운드 간 탈락 항목 비교가 "반복 실패" 판정의 근거가 됩니다. 그래서
`decisions.md`는 **append 전용**입니다 — 덮어쓰면 무한루프 방지가 같이 사라집니다.

## 구조

```
.claude/skills/oss-design-harness/SKILL.md   # 하네스 본체 — 진입 라우터 + 4단계 + 오케스트레이션 배선
templates/brief.md                            # 0단계 산출물 — A단계가 읽어갈 기준값 키 포함
templates/decisions.md                        # B단계 산출물 — 라운드 append 구조
docs/figma-mcp.md                             # Figma MCP 실측 절차·rate limit 대응·폴백
docs/concept.md                               # 컨셉 스펙 전문 (배경·경쟁 포지셔닝·논리 검증 과정)
```

## 사용법 (참가자용)

1. **Figma MCP를 먼저 붙입니다.** `docs/figma-mcp.md`의 실측 절차로 툴 이름을 확인하고 스모크
   테스트를 통과시킵니다. **툴 이름은 환경마다 다르므로 문서의 이름을 믿지 말고 각자 실측합니다.**
   여기서 막히면 화면 제작으로 넘어가지 않습니다 — 만들다가 실패하면 원인이 뒤섞입니다.
2. 이 레포를 프로젝트 루트로 해서 Claude Code(또는 다른 코딩 에이전트)를 실행합니다.
3. `.claude/skills/oss-design-harness/SKILL.md`의 각 `TODO`를 채웁니다 — **이게 당신의 판단기준을
   코드화하는 작업입니다.** 구조는 이미 배선돼 있으니 판단 내용만 채우면 됩니다.
4. `templates/`의 두 파일을 프로젝트 폴더로 복사해 산출물을 남깁니다. 0단계 결과는 `brief.md`,
   B단계 결과는 `decisions.md`. **`decisions.md`는 라운드마다 덧붙이고 덮어쓰지 않습니다.**
5. 완성된 SKILL.md를 팀·코파운더와 공유해 비교합니다.
