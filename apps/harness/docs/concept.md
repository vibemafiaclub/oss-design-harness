# 오픈소스 디자인 하네스 — 컨셉 스펙 (v0, 킥오프 공유용)

> 2026-08-24 최수민-Claude 대화에서 정리. 2026-08-25 20:00 이너서클 오픈소스 코파운더 킥오프 자료.
> 이 문서는 "뼈대"를 담는다 — 구체 내용(프롬프트 문구, 판단 기준값)은 하네스톤 당일 참가자가 채운다. 어디까지가 뼈대이고 어디부터가 채울 몫인지는 본문 하단에 명시.

## 1. 배경

이동은(@iceberg063705) 제안으로, 하네스톤의 최종 목표를 "같이 오픈소스 하네스 만들기"로 잡았다. 하네스톤 당일 산출물(1회성)로 끝내지 않고, 이너서클 지원자들과 함께 분석·개발해 **현업에서 쓸 수 있는 수준의 오픈소스 디자인 하네스**로 발전시킨다. 프로젝트 리딩: 최수민.

## 2. 경쟁 포지셔닝

시장 조사 결과(2026-08-24~25), 경쟁으로 삼을 4개 제품 — **ui-ux-pro-max, Impeccable, Gesso, Pen.dev(구 Pencil)** — 를 조사했다. 넷 다 접근 층위가 다르지만 공통점이 하나 있다.

- **ui-ux-pro-max**: 코드 생성용 규칙 DB(색·타이포·UX 가이드라인) 조회. 오픈소스. Figma 연동 없음.
- **Impeccable**: 코드 에이전트용 설계 어휘팩(59개 슬롭 규칙 + 23개 커맨드). 오픈소스. Figma 연동 없음.
- **Gesso**: 독립 웹앱, Creative Director/UX Architect/Visual Designer 멀티에이전트가 자체 캔버스에서 화면을 생성(직접 실사용 확인, 2026-08-25). 0단계형 확인질문·B단계형 무드 병렬발산·A단계형 토큰 패널까지 우리 프레임과 상당 부분 겹침. 크레딧 기반 유료 SaaS(Free 3,000 크레딧). anti-slop skill(HTML/CSS 73개 결정론적 규칙, MIT)만 부분 오픈소스로 공개. Figma 연동 없음(자체 캔버스).
- **Pen.dev(구 Pencil)**: IDE(Cursor/VS Code) 내장 캔버스, `.pen`(JSON) 파일을 Git으로 버전관리, Claude Code와 자체 MCP로 연동. 2026년 1월 출시, 10만 사용자. 현재 早期 액세스 무료(추후 유료화 예고). Figma 복붙 import는 지원하나 Figma MCP 연동은 아님.

**공통점**: 넷 다 Figma MCP로 실제 `.fig` 파일을 직접 조작하지 않는다. 코드 산출물형(ui-ux-pro-max·Impeccable), 독립 캔버스형(Gesso), IDE 내장 파일형(Pen.dev)으로 갈릴 뿐, **"기존 Figma 파일 안의 컴포넌트·오토레이아웃·배리언트·변수를 직접 조작"하는 자리는 비어 있다.** 우리 하네스톤 참가자는 Figma MCP(`use_figma`)로 정확히 이 자리를 채운다.

**출력 매체는 Figma에 종속되지 않는다.** Figma-네이티브는 이번 하네스톤이라는 검증 무대의 조건(참가자가 Figma로 작업)이지, 프레임워크(0/B/A/C, 아래 4장)의 구조적 전제가 아니다. Figma Pro 구독이 전제되면 시장이 "이미 Figma를 쓰는 프로 디자이너/팀"으로 좁혀지고, ui-ux-pro-max·Pen.dev가 겨냥하는 바이브코더(Figma 없이 코드로 직접 만드는 다수)를 배제하게 된다. 지금은 Figma로 좁게 검증하되(범위 확장은 designboard 문서의 "투기적 설계 금지" 원칙에 위배), 판단기준 추출 로직 자체는 나중에 코드 산출물 등 다른 출력 어댑터에도 이식 가능하도록 설계한다.

## 3. 하네스 컨셉

**"현업 디자이너의 판단 기준(안목)을 추출해, 에이전트에 최적화된 형태로 재구성하는 Figma-네이티브 디자인 하네스."**

### 3.1 왜 "프로세스 재현"이 아니라 "판단기준 추출"인가

당초 "디자이너의 작업 순서를 그대로 재현"하는 컨셉을 검토했으나, 논리 검증 결과 반박됨: 사람의 작업 순서 중 상당수는 **인지적 제약(작업기억·회상 한계)을 우회하기 위한 워크어라운드**이지, 결과를 좋게 만드는 원인이 아니다. 에이전트는 이 제약이 없으므로 순서를 그대로 강제하면 오히려 인위적 병목이 된다.

다만 전부 그런 것은 아니다 — "막연한 요구사항을 명확한 화면 기획으로 좁혀가는" 과정은 **불확실성 해소(발산→수렴)**라는, 실행 주체와 무관하게 필요한 기능이다. 이건 유지하되 구현은 에이전트 특성(병렬 생성·교차 비평)에 맞게 재설계한다.

## 4. 4단계 판단 프레임워크

### 0단계 — 요구사항 정렬

화면을 만들기 **전**, 무엇을 만들어야 하는지 자체가 불확실할 때 클라이언트와 정렬한다.

- **자극은 표상이 아니라 체험이어야 한다.** "모던한 게 좋으세요, 클래시컬한 게 좋으세요?" 같은 라벨형 질문은 클라이언트와 하네스의 어휘 이해가 다를 수 있어 무의미하다. 대신 구체 레퍼런스(스크린샷)를 보여주고 "좋다/싫다 + 왜"를 자유서술로 받는다.
- IA/플로우 같은 구조적 결정도 다이어그램(박스+화살표)으로 보여주면 안 된다 — 다이어그램도 결국 또 다른 전문 표기법이라 라벨형 질문과 같은 함정에 빠진다. **클릭 가능한 로우파이 프로토타입** 또는 **구체 시나리오 내러티브**("아침에 일어나서 앱을 켰다고 해봅시다…")로 체험시킨다.
- 클라이언트의 자유서술 반응에서 하네스가 암묵적 판단기준을 역추출한다. 라벨을 클라이언트에게 요구하지 않는다.
- 확정 안 된 정보는 침묵 처리하지 않고 **가정으로 명시**한다.

### B단계 — 발산·수렴

무엇을 만들지는 정해졌으나 **어떻게 만들지에 정답이 하나가 아닐 때** 진행한다.

- 후보를 만들기 전에 **영향을 주는 독립 축을 먼저 식별하고 분리**한다(예: 비주얼 무드, 정보밀도, UX 직관성 수준). 축을 분리하지 않고 풀스크린 후보를 통째로 비교하면, 클라이언트가 무엇 때문에 선택했는지 뒤섞여(confound) 판단 근거가 안 남는다.
- 축마다 후보를 병렬 생성 → 비교 → 수렴. 사람의 "순차적 스케치"를 흉내내지 않고 에이전트의 병렬 생성 능력을 그대로 쓴다.
- 다각도 검증: 최소 2개 이상 페르소나(예: UX관점/개발호환성관점)로 교차 비평.

### A단계 — 구조적 사실 검증

화면이 다 만들어진 뒤, 데이터/API로 예·아니오 또는 수치로 검증 가능한 것.

- 체크 항목(카테고리)은 하네스에 내장: 컬러 팔레트 일관성, 타이포 스타일 재사용, spacing 그리드 준수, 컴포넌트 재사용률, 레이어 네이밍 semantic 여부, variant 상태 커버리지(존재 여부).
- 체크 기준값(그리드 단위, 네이밍 컨벤션 등)은 프로젝트마다 다르며 0단계에서 추출된 값을 사용.

### C단계 — 미적·게슈탈트 판단

화면이 다 만들어진 뒤, 개별 수치의 합으로 안 잡히는 전체적 지각 판단. **반드시 스크린샷을 렌더해 실제로 봐야** 판단 가능(데이터 조회로 대체 불가).

체크 항목(1회차 심사 리포트 원문 근거):
- 섹션 간 색온도·조명 일관성
- 시각적 위계가 한눈에 읽히는가
- 여백 리듬의 체감 일관성(수치가 맞아도 시각적으로 안 맞을 수 있음)
- 정보 밀도 번잡함 여부
- 클리셰/AI슬롭 여부
- 엣지케이스(빈 상태 등)의 실제 완성도(존재 여부는 A단계, 품질은 C단계)

### C단계 실패 시 라우팅

C단계는 합격/불합격이 아니라 **원인 진단**까지 내야 한다. 원인의 층위에 따라 셋으로 갈린다.

1. **국소적 결함** — 표면 속성 하나의 문제(예: 카드 간격만 불균일). 그 속성만 고쳐 C단계 재검. B단계로 안 돌아감.
2. **방향 자체가 틀림** — 국소 조정으로 안 고쳐지는 구조적 문제. B단계로 회귀해 다른 후보 선택 또는 재발산.
3. **반복 실패** — B단계에서 후보를 바꿔도 같은 이유로 계속 탈락. 요구사항 해석 자체가 틀렸다는 신호 — 0단계로 에스컬레이션.

반복 상한을 두어 무한 루프를 막고, 상한 초과 시 사람(드라이버)에게 에스컬레이션한다. 최종 "이 정도면 됐다" 판단은 항상 사람이 내린다.

## 5. 판단기준이 정해지는 시점 — 3계층

- **완전 고정(하네스 내장, 프로젝트 무관)**: 접근성 대비율(WCAG), 이미지 깨짐 없음 등 객관적 품질 하한선.
- **항목은 고정, 값은 프로젝트별**: A/C단계의 체크 카테고리는 하네스 내장이지만, 구체 기준값(그리드 단위, 밀도 허용 범위 등)은 0/B단계에서 그 프로젝트의 레퍼런스·클라이언트 반응으로 캘리브레이션.
- **완전 프로젝트별**: 특정 도메인에만 있는 기준(예: 사진 기록 앱의 프라이버시 마스킹 자연스러움)은 하네스에 없다가 0단계에서 새로 정의된다.

## 6. 산출물 파일 구조

0/B단계 작업 결과는 반드시 파일로 남겨, 이후 A/C단계와 C실패 라우팅이 참조할 수 있게 한다.

- **`brief.md`** (0단계 산출물): 보여준 레퍼런스 + 클라이언트 반응 원문, 역추출한 암묵적 판단기준, 명시적 가정 로그, 추출된 디자인 토큰 값.
- **`decisions.md`** (B단계 산출물): 식별된 독립 축 목록, 축별 생성 후보·비교 근거·선택 이유, 남은 트레이드오프.

드라이버 스위치 시 인수인계 메모는 이 두 파일에 이어 쓴다. 별도 양식 불필요.

## 7. 팀 운영 구조

### 7.1 페어링 (디자이너 + AI전문가/개발자)

6인 팀을 2인 1조 × 3조로 편성. 역할은 "판단 vs 인코딩"이 아니라 **드라이버(직접 실행) vs 내비게이터(코칭)**로 나눈다 — 이 행사의 도구(Claude Code/Codex 등)가 에이전틱 코딩 하네스라, "스킬 작성"은 자연어 프롬프트 작성에 가까워 디자이너도 직접 할 수 있다.

- **드라이버는 디자이너로 시작**한다. 본인이 직접 SKILL.md를 쓰고 에이전트에게 프롬프트를 준다.
- **내비게이터(AI전문가/개발자)**는 직접 타이핑하지 않고, 프롬프트 구조 코칭과 Figma MCP 연결/API 에러 같은 기술적 장애물 제거를 담당.
- **스위치 트리거**: 디자이너가 판단 기준을 자연어로 다 쏟아내고 1차 프롬프트/스킬 초안까지 직접 써본 시점에 운전대를 넘긴다. 스위치 시점을 1회차부터 있던 **강제 싱크 타임(15~20분 단위)**과 일치시켜 별도 안내 없이 자연스럽게 굴러가게 한다.

이 구조로 "디자이너가 하네스 만드는 법을 배우러 왔는데 피드백만 하다 갔다"는 불만을 방지한다.

### 7.2 인사이트 캡처 장치

- **스위치 시점 인수인계 메모** — `brief.md`/`decisions.md`에 이어 쓰기 (7.1과 결합)
- **싱크 타임 녹음/전사** — 기존 운영장치에 얹어 저비용으로 수집
- **상호 심사 코멘트** (1회차부터 있던 "상호 채점용" 폴더 재활용) — 왜 좋은지/아쉬운지를 언어화

## 8. 지금 확정 vs 하네스톤에서 채울 것

**지금 확정(뼈대) — 논리로 검증됨**
- A/B/C/0 4단계 프레임과 각 단계 정의
- "표상이 아니라 체험" 원칙
- "순서가 아니라 함수" 원칙
- C실패 시 3갈래 라우팅 + 반복상한 + 사람 게이트
- 팀 운영 방식(페어링·드라이버/내비게이터 스위치·인사이트 캡처 3종)
- brief.md/decisions.md 2파일 구조
- 경쟁 포지셔닝

**하네스톤에서 채울 것 — 암묵지·실측 필요**
- C단계 판단기준의 실제 내용(무엇을 보고 "고급스럽다"고 판단하는지)
- 0단계 질문 설계의 실제 문구·레퍼런스 소싱 방법(도메인마다 다름)
- 실제 프롬프트/스킬 코드 구현
- B단계 구체 값(후보 개수, 페르소나 종류·개수, 수렴 기준)
- 프로세스를 스킬로 코드화하는 구체 패턴(1회차부터 미해결)

**참가자에게 넘기는 템플릿의 원칙**: 구조(SKILL.md 형식, brief.md/decisions.md 양식, C실패 라우팅)는 코파운더 테스트로 검증된 완성본을 준다. 단, **판단기준 내용은 예시 2~3개만 남기고 나머지는 비워서** 넘긴다 — 이미 채워진 답을 주면 참가자가 자기 안목을 꺼내는 대신 우리 답을 검토하는 일이 되어, 하네스톤의 본래 목적(다양한 디자이너의 독립적 안목 수집)이 오염된다.

3. **하네스톤 당일(9/5)**: 참가자들이 빈 템플릿을 독립적으로 채운다. 이게 이 프레임워크의 진짜 실증 무대다(designboard Slice 1과 같은 패턴 — 실사용을 첫 베타테스트로 삼음).
