# Figma MCP 연결 — 행사 당일 1순위 병목

이 하네스는 Figma MCP로 실제 `.fig` 파일을 조작한다. **연결이 안 되면 하네스 전체가 멈춘다.**
그래서 화면을 만들기 전에 이 문서의 스모크 테스트를 먼저 통과시킨다.

> ⚠ **툴 이름은 이 문서에 하드코딩하지 않았다.** 참가자 환경마다 서버 종류가 다르고, 서버마다 툴
> 이름이 다르다. 추측한 이름을 적어 두면 당일 존재하지 않는 툴을 호출하는 최악의 결과가 난다.
> 아래 **실측 절차**로 각자 확인해 "실측 기록" 표를 채운다. 이 문서의 값어치는 그 절차에 있다.

## 서버 종류 — 어느 것을 쓰는지 먼저 확정한다

Figma MCP는 최소 세 갈래가 있고 **툴 이름이 서로 다르다.** 자기가 무엇에 붙어 있는지 모르면
남의 툴 이름을 따라 쓰다 실패한다.

| 종류 | 접속 형태 | 확인 방법 |
|---|---|---|
| Figma 공식 **원격** MCP | `https://mcp.figma.com/mcp` (OAuth 필요) | `/mcp` 목록에 원격 서버로 표시 |
| Figma Desktop **로컬** MCP | Figma 데스크톱 앱이 로컬 포트로 노출 | Figma 앱 설정에서 활성화 필요 |
| **서드파티** MCP | 직접 설치한 npm 패키지 등 | 자기 MCP 설정 파일에 있음 |

### 이 레포 작성 환경에서 실측된 것 (2026-09-01)

참고용 1개 사례다. **당신 환경이 같다고 가정하지 마라.**

- 서버: Figma 공식 원격 MCP — `https://mcp.figma.com/mcp` (claude.ai 커넥터 경유)
- 툴 이름 접두어: `mcp__claude_ai_Figma__`
- 상태: **미인증.** 미인증 상태에서는 `authenticate` / `complete_authentication` **두 개만** 노출되고
  실제 파일 조작 툴은 목록에 나타나지 않는다.
- 인증 방법: `/mcp` 실행 → `claude.ai Figma` 선택 → 브라우저에서 승인

★ **미검증 사항**: `use_figma`라는 툴 이름이 실제 존재하는지 확인되지 않았다. 이 레포 초기 문서
(`docs/concept.md`, 초기 `SKILL.md`)가 이 이름을 썼으나, 위 실측 환경의 접두어와 형태가 다르다.
**당일 실측한 이름을 쓰고, 문서의 이름을 믿지 마라.**

## 실측 절차 — 화면 제작 전에 반드시 통과시킨다

1. **`/mcp` 실행.** 연결된 Figma 서버가 어느 종류인지, 인증됐는지 확인한다.
2. **인증한다.** 미인증이면 실제 조작 툴이 목록에 아예 없다 — "툴이 없다"와 "인증이 안 됐다"를
   혼동하지 마라.
3. **노출된 툴 이름을 그대로 옮겨 적는다.** 아래 표에 채운다.
4. **가장 값싼 읽기 툴 1개로 스모크 테스트.** 파일 하나를 조회해 응답이 오는지만 본다.
   여기서 실패하면 화면 제작으로 넘어가지 않는다 — 만들다가 실패하면 원인이 뒤섞인다.

### 실측 기록 (각자 채운다)

| 용도 | 실측한 툴 이름 | 스모크 테스트 결과 |
|---|---|---|
| 파일/노드 트리 읽기 | TODO | |
| 노드 속성 읽기 (A단계용) | TODO | |
| 이미지/스크린샷 렌더 (C단계용) | TODO | |

**C단계용 렌더 툴이 없으면** 스크린샷을 Figma에서 수동 export해 검증 Agent에 넘긴다.
C단계는 스크린샷이 있어야만 성립하므로 이 경로는 반드시 확보한다.

## Rate limit 대응

수치는 서버·플랜마다 다르므로 실측한다. 다만 **이 하네스 구조에서 나오는 위험은 서버와 무관하게
셋으로 정해져 있다.** 셋 다 "같은 정보를 여러 번 조회한다"는 한 가지 실수의 변형이다.

**1. A단계를 항목마다 조회하면 6배가 된다.**
A단계 6항목(색·타이포·spacing·재사용·네이밍·배리언트)은 전부 같은 노드 트리에서 나온다.
→ **노드 트리를 1회 조회해 캐시하고, 6항목을 그 스냅샷 하나로 판정한다.**

**2. B단계 병렬 에이전트가 각자 조회하면 N배가 된다.**
이 하네스는 후보 생성과 페르소나 비평을 의도적으로 병렬로 띄운다(`SKILL.md` B-2·B-3). 각 Agent가
자기 몫을 따로 조회하면 요청이 에이전트 수만큼 곱해지고, **동시에** 터지므로 rate limit에 가장
걸리기 쉬운 지점이다.
→ **부모가 한 번 조회한 스냅샷을 각 Agent 프롬프트에 넣어 준다.** Agent가 직접 조회하게 하지 않는다.

**3. 재시도 루프가 조회를 반복한다.**
C단계 탈락 → 수정 → C 재검 루프에서 매번 전체를 다시 읽으면 라운드마다 배수로 늘어난다.
→ **고친 노드의 서브트리만** 다시 읽는다. 라운드 상한(기본 3)이 이 폭증의 상한도 같이 잡아 준다.

실패 시에는 지수 백오프로 재시도하고, **몇 번째에 풀렸는지 기록한다** — 그게 당일 다른 조에게
줄 수 있는 가장 쓸모 있는 정보다.

## 완전 실패 시 폴백 — 하네스는 계속 굴러간다

Figma MCP가 끝까지 안 붙어도 **0/B/A/C 구조와 판단기준 추출은 그대로 유효하다.** 출력 매체가
바뀔 뿐이다. 당일 이걸로 시간을 다 쓰지 마라.

| 막힌 지점 | 폴백 |
|---|---|
| 조작 툴 없음 (읽기만 됨) | 화면은 Figma에서 수동 제작, A·C단계 검증만 하네스로 |
| 렌더 툴 없음 | 스크린샷 수동 export → C단계 검증 Agent에 첨부 |
| 전부 불가 | A단계를 수동 체크리스트로 강등. C단계는 수동 스크린샷으로 정상 진행 |

폴백으로 갔으면 `brief.md` 가정 로그에 **"A단계를 수동으로 판정했다"**를 적는다. 나중에 결과를
비교할 때 검증 강도가 달랐다는 사실이 남아야 한다.
